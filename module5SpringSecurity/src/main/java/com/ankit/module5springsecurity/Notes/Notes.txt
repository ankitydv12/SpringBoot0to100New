============================================================
jwtAuthFilter in SecurityFilterChain
============================================================

What jwtAuthFilter is
---------------------
`jwtAuthFilter` is a custom Spring Security filter that runs once for each
request because it extends `OncePerRequestFilter`.

Its job is simple:

1. Read the JWT from the request
2. Validate and parse the token
3. Identify the user from the token
4. Put an authenticated object into Spring SecurityContext
5. Let the request continue through the filter chain


Where it is added in WebSecurityConfig
--------------------------------------
Inside `WebSecurityConfig`, the filter is registered here:

    .addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class)

Meaning:

- Spring will run `jwtAuthFilter` before `UsernamePasswordAuthenticationFilter`
- JWT-based authentication happens early in the chain
- If the user is authenticated by JWT, later security checks can use that
  authentication

This is important because `.anyRequest().authenticated()` depends on
`SecurityContextHolder` already containing a valid authentication object.


Why it is needed
----------------
This project uses:

    .sessionCreationPolicy(SessionCreationPolicy.STATELESS)

That means Spring Security will not rely on HTTP session-based login state.
So each request must carry its own authentication data, which is the JWT.

Because of this, the filter must check every incoming request and rebuild the
authentication from the token.


Flow of jwtAuthFilter
---------------------
For each request, the filter does the following:

1. Reads the `Authorization` header

       final String requestToken = request.getHeader("Authorization");

2. Checks whether the header exists and starts with `Bearer `

       Authorization: Bearer <token>

   If not, the filter does nothing and passes the request forward:

       filterChain.doFilter(request, response);

3. Extracts the token value by removing `Bearer `

4. Calls `jwtService.getIdFromJwtToken(token)` to get the user id from the JWT

5. Checks whether:

   - user id was extracted successfully
   - no authentication is already present in `SecurityContextHolder`

6. Loads the user from database/service:

       User user = userService.getById(userId);

7. Creates a `UsernamePasswordAuthenticationToken`

8. Stores that authentication in `SecurityContextHolder`

After this, Spring Security treats the request as authenticated.


Core authentication code
------------------------
    Long userId = jwtService.getIdFromJwtToken(token);

    if (userId != null &&
        SecurityContextHolder.getContext().getAuthentication() == null) {

        User user = userService.getById(userId);

        UsernamePasswordAuthenticationToken authenticationToken =
                new UsernamePasswordAuthenticationToken(user, null, null);

        authenticationToken.setDetails(
                new WebAuthenticationDetailsSource().buildDetails(request)
        );

        SecurityContextHolder.getContext().setAuthentication(authenticationToken);
    }


Role of SecurityContextHolder
-----------------------------
`SecurityContextHolder` stores authentication details for the current request.

When `jwtAuthFilter` sets the authentication there, Spring Security can later
decide:

- whether the request is authenticated
- which controller methods can be accessed
- which user is currently logged in

Without setting `SecurityContextHolder`, protected endpoints would still be
treated as unauthenticated.


Public vs protected endpoints
-----------------------------
In `WebSecurityConfig`:

- `GET /posts` and `GET /posts/**` are public
- `/auth/**` is public
- every other request requires authentication

So if a request goes to a protected endpoint, `jwtAuthFilter` must set valid
authentication before authorization rules are evaluated.


Important observation in this project
-------------------------------------
The current filter reads JWT only from:

    Authorization header

Specifically:

    request.getHeader("Authorization")

So even though earlier notes discuss storing JWT in a cookie, this filter does
not read the cookie named `token`.

That means the current active authentication mechanism in the filter chain is:

    Authorization: Bearer <token>

not cookie-based JWT authentication.

If you want cookie-based JWT authentication, then this filter must be changed
to read the JWT from `request.getCookies()` instead of only checking the
`Authorization` header.


Why addFilterBefore is correct here
-----------------------------------
`UsernamePasswordAuthenticationFilter` is commonly used for username/password
login processing.

Since JWT authentication should happen before Spring reaches that stage,
placing `jwtAuthFilter` before it is the correct design for stateless API
security.


Summary
-------
- `jwtAuthFilter` authenticates each request using JWT
- it runs once per request because it extends `OncePerRequestFilter`
- it is inserted into `SecurityFilterChain` using `addFilterBefore(...)`
- it reads `Authorization: Bearer <token>`
- it extracts user id using `jwtService`
- it loads the user and sets authentication in `SecurityContextHolder`
- this allows protected endpoints to pass `.authenticated()`
- current code is header-based JWT auth, not cookie-based JWT auth
