============================================================
Cookies in authController
============================================================

What is a Cookie?
-----------------
A cookie is a small piece of data that the server sends to the browser.
The browser stores it and automatically sends it back with future requests
to the matching server and path.

Cookies are commonly used to keep a login token between requests. In this
project, the JWT is stored in a cookie named `token` after a successful login.


Cookie Flow in the Login API
----------------------------
1. The client sends login details to:

       POST /auth/login

2. AuthService authenticates the user and generates a JWT.

3. authController creates a cookie containing that JWT:

       Cookie cookie = new Cookie("token", token);

4. `setHttpOnly(true)` marks the cookie as HttpOnly.

5. `response.addCookie(cookie)` sends the cookie to the browser through the
   HTTP `Set-Cookie` response header.

6. The browser stores the cookie and sends it automatically on later
   requests to the same application.


Important Code
--------------
    String token = authService.login(loginDTO);

    Cookie cookie = new Cookie("token", token);
    cookie.setHttpOnly(true);
    response.addCookie(cookie);

The endpoint also returns the token inside `ApiResponse`. Therefore, the JWT
is currently available both in the response body and in the cookie.


HttpOnly Cookie
---------------
`HttpOnly` prevents JavaScript in the browser from reading the cookie through
`document.cookie`. This reduces the impact of many cross-site scripting (XSS)
attacks because client-side scripts cannot directly access the JWT.

HttpOnly does not prevent the browser from sending the cookie with requests,
and it does not protect against every type of attack. CSRF protection and
proper cookie configuration are still important.


Recommended Cookie Attributes
-----------------------------
For a production authentication cookie, configure these attributes:

    HttpOnly  -> JavaScript cannot read the cookie
    Secure    -> Send the cookie only over HTTPS
    SameSite  -> Helps prevent cross-site request forgery (CSRF)
    Path      -> Restricts which application paths receive the cookie
    Max-Age   -> Controls how long the cookie remains valid

The current code sets only `HttpOnly`. `Secure`, `SameSite`, `Path`, and
`Max-Age` should be added according to the deployment environment and the
desired login lifetime.


Cookie Authentication vs Authorization Header
----------------------------------------------
There are two common ways to send a JWT:

    Cookie:
        The browser sends it automatically. Use HttpOnly, Secure, and
        SameSite settings, and consider CSRF protection.

    Authorization header:
        The client sends `Authorization: Bearer <token>` explicitly. This
        is common for APIs and mobile clients, but JavaScript must store and
        read the token somehow.

Choose one consistent approach. If the application authenticates from the
cookie, a JWT filter must read the `token` cookie, validate the JWT, and put
the authenticated user into Spring SecurityContext.
