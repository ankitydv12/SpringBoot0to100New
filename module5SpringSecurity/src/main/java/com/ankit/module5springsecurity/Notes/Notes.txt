Access Token and Refresh Token
==============================

Introduction
------------
In JWT-based authentication, two tokens are commonly used:

1. Access Token
2. Refresh Token

Both tokens work together to keep the application secure while also giving the user a smooth login experience.


What is an Access Token?
------------------------
An access token is a short-lived token used to access protected APIs.

Main idea:
- After login, the server gives the client an access token.
- The client sends this token with each secured request.
- The server checks the token before allowing access.

Purpose:
- To prove that the user is authenticated
- To allow access to protected resources
- To avoid storing session state on the server

Important point:
- Access token should have a short expiry time.
- If it gets leaked, the damage is limited because it will expire soon.


What is a Refresh Token?
------------------------
A refresh token is a long-lived token used to get a new access token.

Main idea:
- When the access token expires, the user should not be forced to log in again immediately.
- The refresh token is used to request a new access token.

Purpose:
- To keep the user logged in for a longer time
- To reduce the need for repeated login
- To separate short-term access from long-term authentication

Important point:
- Refresh token should live longer than access token.
- It should be stored more carefully than the access token.


Why do we need both tokens?
---------------------------
If only one long-lived token is used, security becomes weaker.

If only one short-lived token is used:
- security is better
- but user experience becomes poor because frequent login is required

Using both tokens gives balance:
- Access token gives security
- Refresh token gives convenience


Flow of Authentication
----------------------
Step 1: User logs in
- User sends email/username and password to the server.
- Server verifies the credentials.

Step 2: Server generates tokens
- If login is successful, the server creates:
  - one access token
  - one refresh token

Step 3: Tokens are sent to the client
- Access token is usually returned in the response body.
- Refresh token is usually stored safely, often in an HttpOnly cookie.

Step 4: Client accesses protected APIs
- The client sends the access token in the Authorization header.
- Common format:
  Authorization: Bearer <access_token>

Step 5: Server validates the access token
- Server checks:
  - token is present
  - token is valid
  - token is not expired
- If valid, the request is allowed.

Step 6: Access token expires
- Because access token is short-lived, it expires after some time.
- After expiry, protected API calls will fail if the same token is used.

Step 7: Client uses refresh token
- The client sends the refresh token to a refresh endpoint.
- Server verifies the refresh token.

Step 8: Server issues a new access token
- If the refresh token is valid, the server creates a fresh access token.
- User can continue using the application without logging in again.


Difference Between Access Token and Refresh Token
-------------------------------------------------
Access Token:
- Short-lived
- Used on protected API requests
- Sent frequently
- Should expire quickly

Refresh Token:
- Long-lived
- Used only to get a new access token
- Sent less frequently
- Should be stored more securely


Where are they usually stored?
------------------------------
Access Token:
- Commonly stored on the client side
- Often sent in Authorization header

Refresh Token:
- Preferably stored in HttpOnly cookie
- This reduces exposure to client-side JavaScript

Why this matters:
- Access token is used again and again, so it is more exposed.
- Refresh token gives power to generate new access tokens, so it must be protected carefully.


Important Security Points
-------------------------
1. Access token should be short-lived
- This reduces risk if token is stolen.

2. Refresh token should be protected carefully
- Because it can be used to issue new access tokens.

3. Use HTTPS
- Tokens should never travel over insecure connections.

4. Keep authentication stateless
- JWT is commonly used in stateless systems.
- Server does not need to store login session in memory.

5. Validate token properly
- Server must always check signature, expiry, and identity.

6. Refresh token should not be used as an access token
- Each token has a separate purpose.


Practical Understanding
-----------------------
Think of it like this:

- Access token = temporary entry pass
- Refresh token = permission to get a new entry pass

The user uses the temporary pass many times.
When that pass expires, the refresh token helps get another one without repeating full login.


Why this pattern is useful
--------------------------
- Better security than one long-lived token
- Better user experience than forcing login again and again
- Suitable for modern stateless APIs
- Common in Spring Security + JWT based applications


Summary
-------
- Access token is used to access protected APIs.
- Refresh token is used to generate a new access token.
- Access token should be short-lived.
- Refresh token should be long-lived and stored securely.
- Login creates both tokens.
- Protected requests use access token.
- Token refresh flow avoids repeated login.
